## Question

TypeScript 7 ships its real compiler as native platform binaries via `optionalDependencies` (`@typescript/typescript-win32-x64`, `-win32-arm64`, `-linux-x64`, `-linux-arm`, `-linux-arm64`, `-darwin-x64`, `-darwin-arm64`, `-aix-ppc64`, `-freebsd-arm64`, `-freebsd-x64`, `-linux-loong64`, `-linux-mips64el`, `-linux-ppc64`, `-linux-riscv64`, `-linux-s390x`, and likely more). If `@diego22rct/tenets` depends on `typescript@7`, that pulls this whole platform matrix in transitively for whoever installs/runs our package via `npx`.

Resolve:
1. How does npm/npx actually resolve `optionalDependencies` for platform-specific packages in practice (does it correctly install only the matching platform's binary, the way `esbuild`/`@swc/core`/similar tools already do) — any known gaps for less-common platforms/architectures, or for `npx` one-shot invocation specifically (as opposed to a persisted `npm install`)?
2. What's the install-size/cold-start-time impact for an `npx @diego22rct/tenets <path>` one-shot invocation compared to today's pure-JS `typescript@5.x` dependency?
3. Are there known compatibility issues with common CI environments (GitHub Actions runners, Docker images, etc.) for the native binary approach?
4. Does this change anything about how `@diego22rct/tenets` itself should declare its own dependency (e.g., does it need its own `optionalDependencies` entries, or does depending on `typescript@7` transitively handle it correctly)?

Findings feed into the go/no-go ticket (ts7-003) — packaging/distribution risk is a real input to that decision, independent of whether the API itself is usable.

## Resolution (2026-08-09)

Verified against the live npm registry (`npm view`, `npm pack --dry-run`) for real package sizes, and empirically on this machine (npm 11.17.0, Node 26.5.1, Windows x64) by actually running `npm install typescript@7.0.2` and `npx --yes typescript@7.0.2 tsc --version` after a forced cache clean, plus web research (npm/cli issue tracker, esbuild/sharp/@swc/core precedent, TypeScript 7 announcement posts).

**Q1 — the mechanism works and is well-precedented, but npx has a currently-open, condition-dependent crash bug for exactly this package shape.** npm's installer filters `optionalDependencies` by each platform-package's `os`/`cpu` (and `libc`, when set) fields against the installing machine, adding only the match to the tree — same mechanism `esbuild` (`@esbuild/*`), `@swc/core` (`@swc/core-*`), `sharp` (`@img/sharp-*`), and `rollup` (`@rollup/rollup-*`) already use. Confirmed empirically two ways: (1) a scratch package with `"dependencies": {"typescript": "7.0.2"}` did a plain `npm install` and added exactly 2 packages — `typescript` + `@typescript/typescript-win32-x64` — not all 20 platform variants, proving the filter applies transitively regardless of nesting depth; (2) `npx --yes typescript@7.0.2 tsc --version` (post cache-clean, so a genuinely cold fetch) succeeded cleanly, printing `Version 7.0.2`, with `.bin/tsc` shims correctly created under `~/npm-cache/_npx/<hash>/node_modules/.bin/`. Known gaps found:
- **Regenerated-lockfile bug** (npm/cli#4828, #8320, open discussion for years): if `package-lock.json` is regenerated while `node_modules` already exists (rather than a clean delete+reinstall), npm can capture only the current machine's platform variant, silently dropping the others — later `npm ci` on a different OS/CI container then fails with `Cannot find module @rollup/rollup-linux-x64-gnu`-style errors. Documented as recurring for esbuild/rollup/swc/sharp. Not applicable to npx one-shot users (no persisted lockfile), but relevant to any team that adds `@diego22rct/tenets` as a devDependency instead of running it via npx.
- **Live npm 11.x arborist crash, npx-specific** (npm/cli#9506, open as of ~June 2026; related to the since-partially-fixed #4828/PR #8184): `"Cannot destructure property 'package' of 'node.target' as it is null"` during the `build:links` phase of npx's rebuild step, hit by other tools with platform-filtered `optionalDependencies` (e.g. gitnexus→onnxruntime-web) on npm 11.16.0; `npm install -g` of the same package works fine, only `npx` triggers it. It did **not** reproduce for `typescript@7.0.2` on this machine's npm 11.17.0 — the trigger condition (npm's own root-cause notes point at workspace/symlink targets) isn't fully understood, so this should be read as "a live, real bug class in this exact area of npm, not fully closed out" rather than "confirmed will bite us."
- pnpm does not install `optionalDependencies` by default (Effect-TS/tsgo#383) — `pnpm dlx` users would silently get no native binary unless `install-optional=true` is set. Not an npm/npx issue, but worth a docs note if `pnpm dlx` is ever a supported invocation path.

**Q2 — real numbers via `npm pack --dry-run`, not estimates.** `typescript@5.9.3` (pure JS): 4.4 MB compressed / 23.6 MB unpacked, 132 files, one package. `typescript@7.0.2` wrapper (JS glue + vendored RPC libs, no compiler): 365.6 kB compressed / 2.5 MB unpacked, 416 files. Plus exactly one platform binary — e.g. `@typescript/typescript-linux-x64@7.0.2`: 9.7 MB compressed / 27.9 MB unpacked, 114 files, dominated by a single 24.1 MB native `lib/tsc` binary (win32-x64 and darwin-arm64 packages are essentially the same size, 28.0–28.4 MB unpacked). **Total real-world single-platform install: ~10.1 MB compressed / ~30.4 MB unpacked — about 2.3x more to download and 1.3x more on disk than today's `typescript@5.9.3`.** Splitting the binary per-platform avoids downloading the other 19 variants, but the one variant you do need is not smaller than the pure-JS baseline — it's larger. Cold-start network cost for a first-ever `npx @diego22rct/tenets` on a given machine: roughly 5.7 MB more compressed download than the current ts5.x-based tool; likely low-hundreds-of-ms to a couple seconds extra on typical broadband, near-negligible on CI runners with fast registry mirrors. Runtime cold-start is a different model, not size-driven: native compiler is a spawned subprocess (one-time spawn cost, measured at ~171ms on the machine used for the companion ts7-001 research) vs. today's in-process JS parse — likely a wash or net win for anything beyond a trivially small codebase given TS7's ~10x steady-state throughput, but adds a subprocess-spawn floor that pure-JS `typescript@5.x` doesn't have. npx caches the download under `~/.npm/_npx/<hash>` (confirmed the platform binary lands there), so only the very first invocation on a given machine pays this cost — repeat runs reuse the cache and the size delta stops mattering.

**Q3 — lower risk than the sharp/swc precedent on the musl/Alpine axis, same systemic npm-level risks otherwise.** GitHub Actions hosted runners (`ubuntu-latest`/`windows-latest`/`macos-latest`) are standard glibc/native OS images, not musl, and match platforms TypeScript 7 already ships (`linux-x64`, `linux-arm64`, `win32-x64`, `win32-arm64`, `darwin-x64`, `darwin-arm64` all present) — no special CI configuration needed there. The well-known Docker/Alpine failure mode for native npm packages (`sharp`, `@swc/core` both ship separate `*-musl` builds because their binaries are dynamically linked against glibc and crash or fail to load under Alpine's musl libc — lovell/sharp#3159, homarr-labs#4548 "Sharp Library Core Dumps... with Alpine-based Docker Image") looks structurally less likely to apply to TypeScript 7: its `optionalDependencies` list has no separate `*-musl` variant at all (checked directly against the registry), consistent with Go toolchains producing CGO-free, statically-linked binaries by default that don't dynamically link libc and are expected to run unmodified on both glibc and musl hosts (corroborated by an unrelated tsgo-adjacent project's issue notes explicitly distinguishing "tsgo's own CLI works on Alpine because it ships CGO-free static binaries" from wrapper projects that add a cgo/NAPI bridge and do break on musl). Caveat: I could not find a source that has actually run `@typescript/typescript-linux-x64`'s `tsc` binary inside an Alpine container to confirm this directly — treat as "likely fine by construction, not independently verified for this exact binary." The two real, well-documented CI risks are the same ones from Q1: the regenerated-lockfile bug (concretely reported for rollup in Docker builds — vitejs/vite#15532, `Cannot find module @rollup/rollup-linux-x64-gnu on Docker container`) and the open npm 11.x npx arborist crash — both are npm-level issues affecting every native-binary-via-optionalDependencies package today, not something specific to or worse for TypeScript 7.

**Q4 — nothing extra needs declaring; depending on `typescript@7` in `dependencies` transitively just works.** Empirically confirmed (see Q1): a package that simply lists `"typescript": "7.0.2"` in its own `dependencies` and gets installed with plain `npm install` ends up with exactly the right platform binary on disk, with no `optionalDependencies`, `os`, or `cpu` fields declared on the consuming package itself — npm's installer walks the dependency graph at any depth and filters by the actual install machine regardless of how deep `typescript` sits in the tree. `os`/`cpu`/`optionalDependencies` fields on a package's own `package.json` are only meaningful when that package is itself publishing platform-specific binaries, which `@diego22rct/tenets` would not be doing here — it would just be consuming `typescript@7`'s. The only genuinely useful additions, informed by the risks above, are process/docs-level rather than manifest fields: an `engines.node` floor consistent with what `typescript@7.0.2` itself requires (`>=16.20.0`), a note for consumers who `npm install` (rather than `npx`) the tool to avoid regenerating lockfiles from stale `node_modules`, and — only if `pnpm dlx` is ever an explicitly supported invocation path — a note about pnpm's `install-optional=true` requirement.

**Bottom line for ts7-003:** the platform-binary distribution mechanism itself is sound, standard, and (per Q4) requires zero extra work from `@diego22rct/tenets`'s own manifest. The concrete costs are a real ~2.3x compressed / ~1.3x unpacked install-size increase over `typescript@5.x` on every cold `npx` run (one-time per machine, cached after), and CI/Docker risk that's no worse than — and on the musl/Alpine axis structurally better than — established native-binary precedents like `sharp`/`@swc/core`. The one open wildcard is the npm 11.x npx arborist crash (#9506): real, currently unresolved upstream, hits this exact optionalDependencies shape for other tools, but did not reproduce against `typescript@7.0.2` in direct testing here. Worth a note that this is a packaging risk *independent of* the API-maturity finding from ts7-001 (TypeScript 7.0 ships without a stable programmatic API, with 7.1's API "expected to be different" and no date set) — even if packaging risk is judged acceptable, the sibling research means there is currently no in-process API for `@diego22rct/tenets`'s adapter to call at all.
